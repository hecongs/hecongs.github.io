测试流水线里，Jenkins 反复做的是同一类事：在有设备的机器上跑已经定过的用例，把结果变成 JUnit 和邮件，把上一环的产物交给下一环。下面按场景列出难点。`XXXX` 换成自己的任务名、路径和标签。

安装 Controller 和 Agent，见《从零搭起 Jenkins：Controller 和 Windows Agent》。节点控制、JUnit 邮件和压缩包透传的写法，见《Jenkins 流水线难点：节点、JUnit 邮件、压缩包透传》。

## 1. 把用例派到有设备的机器

Controller 只编排。用例必须跑在插着被测设备、标签为 `XXXX` 的 Agent 上。

难点是标签和在线状态。标签差一个字母，构建会一直等 executor。Agent 中途掉线，这一次构建失败，节点恢复后也不会续跑。

## 2. 跑仓库里的版本，不跑工作区里的改动

定时任务和下游任务检出的是 Git 上的分支或标签 `XXXX`。Agent 磁盘上还没提交的修改不会进这次构建。

难点是复现。要重跑某一次失败，把当时的提交号或标签写进任务参数，不要在 Agent 上改完文件就再点一次构建。

## 3. 一次构建里跑多套用例

一套结束，`report.xml` 会被下一套覆盖。每套结束先复制成 `XXXX.xml`，`junit` 的 `testResults` 要把这些副本包括进去。

难点是趋势图只剩最后一套，或者后一套失败把前一套的通过记录盖掉。复制必须发生在下一套启动之前。

## 4. 通过和失败发给不同的人

JUnit 负责页面上的趋势。邮件另外生成：脚本读 `report.xml` 写出 `XXXX.html`，`emailext` 再发出去。通过用收件人参数 `XXXX`，失败用另一个参数 `XXXX`。

难点有三处。SMTP 没在系统配置里写好，流水线里的 `to` 不会发出去。两套任务共用一个目录时，后一套会读到前一套留下的 html。下游收件人不会继承上游参数，触发时要显式传。

## 5. 编译机的压缩包交给测试机

编译和测试常常不在同一台 Agent。上游 `archiveArtifacts` 归档 `XXXX.zip` 和一份写明文件名的清单，并把这次构建号传给下游。下游用 `specific(构建号)` 做 `copyArtifacts`。

难点是 `lastSuccessful()`。上游还没结束时，它指向的是上一份成功的包。`copyArtifacts` 的 `target` 相对 `WORKSPACE`，不跟着 `dir()` 走。上游还要在 Permission to Copy Artifact 里允许任务 `XXXX` 来取，否则目录是空的。

## 6. 定时只跑已经定过判定的项

夜间或版本更新后重跑的，是核心项 `XXXX`，不是全部手工探索。失败要进报告和邮件，不能只留在控制台的红字里。

难点是把环境失败和用例失败标成同一种红色。设备没上线、脚本报错、断言失败要在报告里分开，否则第二天无法决定改环境还是改用例。

## 7. 某一步会切断 Agent 到 Controller 的连接

重启被测设备、切换网络、让 Agent 短暂离线，都不能写在同一步里干等。连接一断，这一步失败，构建结束。

难点是等待时间。先放开 Agent，再在本机用独立于这次 `bat` 的方式做那件会断线的事，Controller 过 `XXXX` 秒后再重新申请节点。秒数按链路真正断开的时刻来定。节点后来变绿，只说明下一次可以派发，不能把已经结束的构建点成继续。

## 8. 重装或重启之后对不上

Controller 重装、Agent 机器重启、服务账户换人，是最常把流水线打回「昨天还能跑」的情况。

对着这几项看：Agent 服务在运行，节点页是在线；secret、节点名和 Controller 地址还是这一套；标签和 Jenkinsfile 逐字相同；服务账户是跑用例的那个用户，能执行构建要用的命令；上游允许下游复制制品。
