网页放在服务器上。测试机主动连到这台服务器，拉仓库里的代码，按用例编号执行 Pytest，再把结果交回去。板上的串口、电源插座、需要切换的 USB 口不由网页直接打开，由跑在测试机上的 Labgrid 占用。下面的 `XXXX` 是占位。

## 各放在哪

| 位置 | 放什么 |
|---|---|
| 服务器 | 网页、接口、数据库、任务队列；用例编号、步骤、期望；测试床是否空闲 |
| 仓库 | Pytest。函数上的标记和平台编号是同一个字符串 |
| 测试机 | 代理进程、一份干净的代码目录、Python、Labgrid 的 exporter |
| 被测板 | 串口、电源、网口。线插在测试机上，不插在服务器上 |

平台发下去的内容只有三样：分支或提交号、用例编号列表、这一次运行的编号。测试机不接受一段临时拼出来的脚本。

## 网页和接口

网页用 Next.js，接口用 Nest.js，两边都是 TypeScript。分成三个进程，不要写在同一个 Node 进程里。

| 进程 | 技术 | 做什么 |
|---|---|---|
| 网页 | Next.js | 用例列表、勾选编号、看测试机是否空闲、看这一次的结果和日志 |
| 接口 | Nest.js | 登录、用例编号、占用测试机、把任务放进队列、按编号回写 |
| 代理 | Node，单独进程 | 跑在测试机上。连着 Nest.js，拉代码，跑 Pytest，交 `report.xml` |

浏览器只访问 Next.js。Next.js 再调用 Nest.js 的接口。浏览器不连接测试机，也不打开串口。

Nest.js 前面用 Nginx。点执行之后，接口先把这次运行写入 PostgreSQL，再放进 Redis 队列，然后马上返回。真正的等待在队列工人里，不占着这次网页请求。库和队列各管什么，见下一节。

工人从队列取出任务编号，再回 PostgreSQL 读取分支、用例编号和要占用的测试机，然后发给已经连在 Nest.js 上的那台代理。代理是测试机开机就启动的进程，主动连出服务器。连接断了，Nest.js 把这台床在库里标成不可用。Pytest 跑几小时，只占测试机上的代理，不占 Next.js。

Next.js 不负责 WebSocket，也不在页面接口里执行 `git` 或 `pytest`。那两个一重启，正在跑的任务和测试机连接会一起断。Next.js 和 Nest.js 分开部署。代理的代码可以和 Nest.js 放在同一个仓库，但是部署在测试机上。

```text
浏览器
  → Next.js          页面
  → Nest.js          读写真相，往队列里放任务
       ├── PostgreSQL  用例、测试床、运行记录、每条编号的结果
       └── Redis       待执行队列、测试机心跳
       ↑ 长连接
  测试机上的代理      拉代码、跑 Pytest
       → exporter    串口、插座
```

## PostgreSQL 和 Redis

PostgreSQL 存必须留下的记录。Redis 只放正在排队和马上会过期的状态。Redis 清空之后，页面上的用例和历史结果还在；正在排队、还没被取走的任务要靠库里的运行记录重新放进队列。

PostgreSQL 里至少有这些：

- 用例：编号、标题、步骤、期望、需求号。
- 测试床：名字、能力、空闲还是占用、占用到哪一次运行。空闲状态写在这里，不写在 Redis。只放在 Redis 里的话，重启后两个人会排到同一台机器。
- 运行记录：分支、提交号、选中的编号、状态（排队、执行中、结束）、基础设施失败原因。
- 每条编号的结果：PASS、FAIL、SKIP，以及日志文件的路径。日志正文放在磁盘上，库里只留路径。把整份日志塞进 Redis，内存会先被打满。

Redis 里只放两样：

- 队列。页面一点执行，Nest.js 先把运行记录写成「排队」，再把运行编号推进 BullMQ。工人取出的是这个编号，然后回 PostgreSQL 读完整内容。队列消息里不复制用例步骤和脚本。
- 心跳。代理每隔一段时间写一个会过期的键，表示自己还连着。键过期，Nest.js 把库里的测试床改成不可用。心跳本身不作为「这台机器可以接新任务」的依据，能否接任务看库里的占用字段。

一次点击之后的写入顺序是固定的：先在 PostgreSQL 里插入运行记录并占住测试床，成功后再推进 Redis。只推进队列、库里还没有记录，工人取出来会找不到这次运行。库里占住了但队列推进失败，页面上会停在排队，需要能再次推进，不能再占一次机器。

## 一次执行

1. 人在页面上勾选编号，并指定分支。
2. 服务器写成一条运行记录，在空闲测试机里占住一台。占不住就继续排队，不能把第二份任务送到同一台。
3. 任务沿测试机早已建立的连接送下去。
4. 测试机在独立目录里取到指定提交。工作区不干净，或取不到这个提交，这次运行记为基础设施失败，不开始 Pytest。
5. 对编号做收集。一个编号对应零个函数，或对应多个函数，都停止并回写原因。数量一致才执行。
6. 执行前向 Labgrid 占用这台床上的串口和电源。占用失败同样记为基础设施失败。
7. Pytest 只跑这些编号，写出 `report.xml`。
8. 无论通过还是失败，都释放 Labgrid 占用，再把 XML 和日志交回服务器。服务器按编号回写，然后把测试机标为空闲。

收集到 0 条仍返回成功，平台会显示全部通过。这一步必须当成失败。

## Labgrid 管端口

Labgrid 把「插在哪」从用例里拿掉。用例写资源名，例如控制台和 1 号插座。真正的设备节点由 exporter 在测试机上匹配。

exporter 和线缆在同一台测试机上。它按 USB 序列号找到串口，不写 `ttyUSB0`。线重新插过之后，内核可能把同一根线编成 `ttyUSB1`，序列号不变，匹配仍然有效。电源写 PDU 的地址和插座序号，用例只调用开、关、重启。

协调器保存「这一组资源叫这个名字」。Pytest 开始时占用这个名字，结束时释放。占用期间，另一条运行拿不到同一组串口和插座。

```text
服务器上的协调器
    ↑ 测试机主动连接
测试机上的 exporter
    ├── 串口  匹配 USB 序列号 XXXX
    └── 电源  PDU XXXX 的插座 N
Pytest 占用该名称后，通过驱动打开串口、控制插座
```

用例里打开的是已经占用到的控制台，读启动日志、等待登录提示符。重启插座之后，原来的串口会话会断，要重新打开，再等新的启动完成。不等提示符就发命令，会把命令打进启动过程，后面的登录全部失败。

平台上的「测试机占用」和 Labgrid 的「资源占用」是两把锁。只锁测试机、不占用串口，另一条人工调试会把口抢走。只占用 Labgrid、平台仍显示空闲，第二个人会再派一次任务。两把锁在同一次运行里一起拿、一起放。Pytest 被杀死时，要有超时把两把锁都释放，否则这台床会一直显示占用。

## 实现时容易错的地方

**编号。** 平台和仓库各改各的，字符串必须完全相同。执行前先列出对不上的编号：平台有而仓库没有，仓库有而平台没有，一个编号对应多个函数。有任何一条，就不开始跑。

**代码目录。** 每次运行使用只属于这次运行的目录，记录拉到的提交号，并随结果回写。两个任务共用一个目录时，后一次拉取会换掉前一次正在跑的代码。

**连接。** 测试机主动连服务器。实验室在 NAT 后面时，用穿透把这条连接送出去。穿透断开要标成基础设施失败并释放占用，不能让页面停在执行中。

**端口。** 串口匹配写序列号，电源匹配写插座号。有人把 `ttyUSB0` 写进用例或写进平台配置，插拔一次后命令会发到另一块板。exporter 没启动时，协调器里看得到名字，打开串口会失败。这种失败发生在断言之前。

**结果。** XML 里的名字要能回到平台编号。对不上的失败会变成「未执行」。日志上传中断时，状态已经写上，附件是空的，页面上要能看出附件缺失。

**环境。** 拉代码失败、依赖装不上、占不到串口、重启后没有登录提示符，记在这次运行的基础设施上。产品断言失败才记在对应用例上。

## 建议的最小接法

服务器跑 Next.js、Nest.js、数据库、Redis 队列和 Labgrid 协调器。测试机跑代理、exporter，以及只属于当前任务的代码目录。代理收到任务后的顺序固定为：取到指定提交、核对编号、占用 Labgrid、跑 Pytest、释放、回写。

页面上先只做编号列表、测试机空闲状态、一次运行的结果和日志。串口和电源不出现在网页上，避免两个人同时点同一路插座。
