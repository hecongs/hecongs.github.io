> **面向协议栈测试工程师的 Host / HCI / Controller 深度剖析**

## 摘要

蓝牙低功耗协议栈由 Host、HCI、Controller 三段构成。这一划分并非实现偏好，而是核心规范为满足"射频与时序高度耦合、上层语义快速演进"这一矛盾所做的工程妥协。对协议栈测试工程师而言，该结构最重要的推论是：**分层边界同时就是可观测边界与责任边界**。

本文围绕三个问题展开。第一，这条边界在字节级、时序级、资源级分别传递什么、丢弃什么；第二，这些"丢弃"如何转化为可复现的缺陷模式；第三，预算有限时该优先测什么，以及在 Zephyr 这类开源协议栈上怎么落地。

核心结论有三条：

1. **绝大多数"蓝牙连不上、吞吐低、偶发断连"的现场问题，根因落在 HCI 边界的资源记账与时序预算上，而非射频或应用逻辑。** 因此测试重心应从功能用例前移到边界资源与时间预算的验证。
2. **HCI 是全栈唯一的标准化截面，也是唯一能用一个抓包工具看到全部状态机迁移的位置。** 任何以"复现困难"为由跳过 HCI 抓包的分析，都缺少关键证据链。
3. **协议栈测试的价值不在覆盖命令表，而在构造能让边界暴露的资源与时间压力。** 命令表的覆盖率可以靠 PTS 达成，边界失效只能靠针对性设计。

## 1 分层契约的形成与代价

### 1.1 三段式结构的规范依据

核心规范在架构层面把设备划分为 Controller 与 Host 两个子系统，并在其间定义 HCI 作为唯一接口。Controller 负责物理层与链路层，包括调制解调、跳频、ARQ、加密引擎、事件调度；Host 负责逻辑链路控制与适配层之上的全部语义，包括 L2CAP、ATT/GATT、SMP、GAP 以及各类 Profile。

这一划分的合理性来自两类组件的演进速率差异。射频与链路层时序由规范严格约束，7.5 ms 的连接间隔下限、150 µs 的帧间隔（tIFS）十几年未变；而上层语义几乎每个版本都在扩张——从 4.2 的数据长度扩展，到 5.2 的等时通道，到 6.0 的信道探测。把两者分离，使上层可以用通用处理器和通用操作系统实现，下层则用紧耦合的中断与硬件定时器实现。

### 1.2 契约带来的三项可替换性

**认证可拆分。** 一致性测试中，Host 子系统与 Controller 子系统分别验证。产品可以用一颗过了 Controller 认证的芯片，搭配自研 Host，二者互不牵连。

**供应链可拆分。** 同一套 Host 可以配不同厂商的 Controller。只要 HCI 行为一致，上层代码零改动。

**软件可独立升级。** Controller 固件可以单独修复射频缺陷，Host 可以单独增加 Profile。

### 1.3 契约的代价：跨边界信息损失

HCI 是一份**面向功能、非面向时序**的接口。它规定了"做什么"，几乎不规定"多久做完"。因此有三类信息在跨越边界时被系统性丢弃：

| 信息类型 | 在 Controller 侧存在 | 跨过 HCI 后变成 | 测试后果 |
|---|---|---|---|
| 精确时间戳 | 锚点、收发包的微秒级时刻 | 事件到达 Host 的时刻（毫秒级抖动） | 无法从 Host 侧判断丢包是空口问题还是调度问题 |
| 失败细节 | CRC 错、白化错、AA 不匹配、ARQ 重传次数 | 统一为"没收到" | 无法区分干扰、距离、同步漂移 |
| 资源状态 | TX/RX buffer 占用、调度冲突 | 只暴露为流控信用数 | 队列积压原因不可见 |

这三类丢失是设计使然，不是缺陷。**测试设计必须补偿它们**：要么在 Controller 侧增加可观测点（厂商 HCI 扩展事件、GPIO 打点、RTT 日志），要么在外部用空口抓包交叉验证。

### 1.4 对测试的直接推论

由此得到本文的方法论基础：**分层边界即观测点，观测点即用例设计入口。** 每一个边界至少需要三类用例——正常穿越、边界值穿越、资源耗尽时的穿越。

## 2 HCI 层：被低估的测试主战场

### 2.1 分组格式与字节级结构

HCI 共五类分组，由首字节的类型指示区分。在 UART 的 H4 传输上，该字节直接出现在字节流中；在 USB 与 IPC 上则由端点或消息类型隐式表达。

| 类型 | 指示字节 | 方向 | 作用 |
|---|---|---|---|
| Command | 0x01 | Host → Controller | 控制面请求 |
| ACL Data | 0x02 | 双向 | 异步数据面 |
| Synchronous Data | 0x03 | 双向 | BR/EDR 的 SCO/eSCO 语音 |
| Event | 0x04 | Controller → Host | 控制面响应与异步通知 |
| ISO Data | 0x05 | 双向 | LE Audio 的 CIS/BIS 等时数据 |

ACL 分组的 4 字节头是排障中信息密度最高的字段，其位域必须逐位理解：

| 位域 | 宽度 | 语义 | 常见误判 |
|---|---|---|---|
| Handle | 12 bit | 连接句柄，0x0000–0x0EFF | 与 Connection Handle 在事件中的含义一致，但 0x0FFF 为广播保留值 |
| PB | 2 bit | 00 首片不可冲刷 / 01 续片 / 10 首片可冲刷 / 11 完整 PDU | 收到 00 后必须跟 01，否则是 Host 分片逻辑 bug |
| BC | 2 bit | 00 点对点 / 01 活跃广播 | 广播包误入连接通道时该位可作判据 |

命令操作码由 OGF 与 OCF 组合而成，`opcode = (OGF << 10) | OCF`。分组空间本身即是一张测试地图：

| OGF | 领域 | 测试关注点 |
|---|---|---|
| 0x01 | Link Control | BR/EDR 建链，LE 产品多不实现，需验证返回 Unknown Command |
| 0x02 | Link Policy | 同上 |
| 0x03 | Controller and Baseband | Reset、Set Event Mask、Read Buffer Size 等初始化命令 |
| 0x04 | Informational | 本地版本、支持的命令与特性位图，是能力协商的根 |
| 0x05 | Status | 读 RSSI、计数器，常用于产测 |
| 0x06 | Testing | Direct Test Mode，射频认证入口 |
| 0x07 | LE Controller | LE 主体，命令量最大 |
| 0x08 | LE Audio | 5.2 引入的 CIG/BIG 与 ISO 数据路径 |
| 0x3F | Vendor Specific | 厂商扩展，兼容性风险集中区 |

### 2.2 命令与事件的配对模型

每条命令必须有且仅有一个终态响应，但"终态"有两种形态：

- **Command Complete**：命令已执行完毕，返回参数随事件带回。
- **Command Status**：命令已被接受，结果稍后以独立事件通知。

二者的区分是时序测试的关键。以连接建立为例，`LE Create Connection` 返回 Command Status，真正的结果通过 `LE Connection Complete` 事件异步到达，中间可能间隔数十毫秒到数秒（取决于扫描窗口与广播间隔）。测试若在发送命令后立即断言连接成功，必然产生误判。

LE 相关的一切几乎都封装在 `LE Meta Event`（Event Code 0x3E）的子事件中。这一设计使规范可以在不新增事件码的前提下持续扩张能力，也让解析器必须具备按子事件码分派的能力。一个常见缺陷是：抓包工具版本落后于固件，遇到新子事件时降级为"未知事件"，导致关键时序证据缺失。

### 2.3 双向流控的信用记账

流控是 HCI 最容易出错的机制，因为它有两个**独立**方向，且记账主体不同。

**Host 到 Controller 方向**由 Host 记账。初始化阶段通过 `LE Read Buffer Size` 获得两个参数：单包最大长度与 Controller 可缓存的 ACL 包总数。Host 每发送一包扣减一次信用，Controller 通过 `Number Of Completed Packets` 事件按连接句柄归还。信用的归还不是"包发出去就还"，而是**空口确认之后才还**，因此该方向的有效吞吐受往返时延约束。

**Controller 到 Host 方向**由 Controller 遵守。Host 通过 `Host Buffer Size` 或 `LE Read Buffer Size v2` 声明自身缓冲能力，Controller 不得超过。这一方向在实践中经常被忽略：跨核或外挂控制器的场景下若不启用主机侧流控，Controller 会持续灌注数据直至 Host 缓冲耗尽。

记账模型的三个可测推论：

1. **信用归还是延迟的，因此队列必然存在。** 队列深度等于 Controller 侧 buffer 数，与 Host 侧 buffer 数取小值。
2. **两个方向的瓶颈可能不同。** 单向大流量（如固件升级）时，瓶颈通常在 Host 到 Controller 方向的信用数；双向小包（如 HID）时，瓶颈在事件处理能力。
3. **信用泄漏会产生"逐渐变慢"的特征。** 若某条错误路径丢失了 Completed Packets 事件，表现为随时间线性下降的吞吐，最终完全阻塞。这是极难用功能用例发现的缺陷，必须用长时压力测试暴露。

### 2.4 传输层差异及其故障模型

HCI 的逻辑一致性由规范保证，物理可靠性由传输层决定。同一份 Host 代码在不同传输上的失效模式完全不同：

| 传输 | 典型速率 | 251 字节 ACL 单包代价 | 主要故障模型 |
|---|---|---|---|
| UART H4 | 1 Mbaud | 约 2.6 ms | 无流控时溢出丢字节；无重传 |
| UART H5 | 1–4 Mbaud | 0.65–2.6 ms | 有 SLIP 封装与序号重传，但重传会放大延迟 |
| SPI | 数 Mbps | 数百微秒 | 需外部中断信号，时序依赖片选与 IRQ |
| USB | 12/480 Mbps | 受帧调度约束 | Bulk 传输延迟不确定，等时通道需专用端点 |
| 共享内存 / IPC | 数十 Mbps | 约 100 µs | 跨核版本不匹配，无协议内版本协商 |

UART 的数字值得特别注意：1 Mbaud 下传输一个满长 ACL 包需 2.6 ms，而连接间隔可能只有 7.5 ms。这意味着**串口本身就能吃掉三分之一的时隙预算**，此时提高空口 PHY 或增大 PDU 都不会改善吞吐，瓶颈在线缆上。这是"性能调优方向错误"的典型来源。

### 2.5 厂商扩展带来的兼容性风险

OGF 0x3F 是规范留给厂商的自由区。它带来能力扩展的同时，引入了三类风险，必须在兼容性测试中显式覆盖：

- **能力探测失败**：Host 依赖某条厂商命令判断芯片型号，遇到新固件返回 Unknown Command 后进入错误分支。
- **事件冲突**：厂商自定义事件的 Event Code 与规范后续版本新增的事件码碰撞。
- **状态污染**：厂商命令修改了规范未定义的内部状态，导致后续标准流程异常。

测试策略是把厂商扩展视为**不可信输入**：在所有标准流程用例中，额外跑一遍"厂商扩展被禁用"的配置，验证标准路径仍可工作。

## 3 Host 栈的关键语义与失效模式

### 3.1 L2CAP 的三层长度关系

L2CAP 之上的一切问题，追根溯源常是三个长度参数不自洽：

- **LL PDU 载荷**：由数据长度扩展决定，最大 251 字节。
- **L2CAP PDU**：4 字节头（长度 + 通道号）加载荷，载荷上限即 L2CAP MTU。
- **ATT PDU**：上限为 ATT_MTU 减 1（ATT 头占 1 字节）。

三者必须满足单调关系：ATT_MTU ≤ L2CAP MTU，且 L2CAP MTU 加 4 字节头不超过 HCI 层 ACL 单包上限。任一处不足，都会引发 HCI 层分片或 L2CAP 层分片，性能骤降。

Zephyr 的默认值恰好构成一个易踩的陷阱：`BT_BUF_ACL_TX_SIZE` 默认 27，对应 L2CAP PDU 27 字节，即 ATT 净荷 23 字节——这正是 ATT 默认 MTU。这意味着**不做任何配置修改时，单次写操作最多承载 20 字节应用数据**。传输固件、图像、日志等大块数据时，必须先同时调大 ACL 缓冲尺寸与 L2CAP MTU，否则表现为"MTU 协商成功但吞吐仍极低"，因为协商结果被下层缓冲截断。

### 3.2 ATT/GATT 的可靠性语义

GATT 提供三种写与两种通知，语义差异经常被混用：

| 操作 | 可靠性 | 代价 | 适用 |
|---|---|---|---|
| Write Without Response | 无确认，可丢 | 最低 | 高频传感器采样 |
| Write Request / Response | 逐包确认 | 一个往返 | 配置写入 |
| Signed Write Without Response | 有签名无确认 | 低 | 需来源认证的高频数据 |
| Handle Value Notification | 无确认 | 低 | 状态推送 |
| Handle Value Indication | 有确认 | 高 | 关键事件 |

两个高频缺陷模式：其一，用 Notification 传关键配置，链路抖动时静默丢失，表现为"偶尔设置不生效"；其二，在 Notification 回调中执行阻塞操作，堵死 Host 接收线程，进而影响所有连接的收发。

MTU 交换本身也有陷阱：`Exchange MTU` 是客户端发起、双方各报自身接收能力，最终取较小值。若服务端在交换前就按大 MTU 构造通知，会被分片或截断。

### 3.3 SMP 的状态机陷阱

配对流程分为特征交换、密钥生成、认证、密钥分发四个阶段，LE Legacy 与 LE Secure Connections 的路径不同。测试中最容易漏的是**部分成功**状态：

- 配对成功但密钥分发不完整，导致后续加密请求失败。
- 绑定信息写入持久化失败，重启后需要重新配对。
- 双方 IO 能力组合落入了规范未定义的组合，行为依赖实现。

这些场景在小样本功能测试中几乎不会出现，必须构造 IO 能力矩阵（DisplayOnly、DisplayYesNo、KeyboardOnly、NoInputNoOutput、KeyboardDisplay）做穷举。

### 3.4 ISOAL 的时间语义

等时通道引入了"时间"这一新的正确性维度。ISOAL 的职责是把 SDU 的时间基准与 ISO 间隔对齐，分为 framed 与 unframed 两种模式：当 SDU 间隔是 ISO 间隔的整数倍时可用 unframed，否则必须 framed 并携带时间偏移。

测试要点不在数据正确性，而在**时间正确性**：SDU 的呈现时刻偏差、丢失 SDU 后的补偿策略、收发两端时钟漂移累积。这些指标无法用"数据对不对"判断，必须测量时间戳序列的抖动分布。

### 3.5 Host 的资源模型

Host 侧只有三个可调资源：缓冲、线程、队列。三者与四类角色的关系如下：

| 资源 | 典型配置项 | 耗尽表现 |
|---|---|---|
| 发送 ACL 缓冲 | 包数、单包长度 | 写操作返回内存不足 |
| 接收 ACL 缓冲 | 包数、单包长度 | 大包被丢弃或连接被流控挂起 |
| 事件缓冲 | 包数、单包长度 | 扫描报告丢失、连接事件漏处理 |
| 接收线程栈 | 栈大小 | 回调深层调用时栈溢出 |
| 发送线程栈 | 栈大小 | 驱动内部加密或分片时溢出 |

一个反直觉的事实是：**接收路径的缓冲需求往往高于发送路径**。因为发送可以阻塞等待，接收不能——空口不会因为你没准备好而暂停。因此调优时应优先保证接收侧余量。

## 4 Controller：时序约束的量化

### 4.1 三层执行上下文

开源 Controller 通常分为三层，理解其执行上下文是分析实时性问题的前提：

- **链路层状态机（Upper Link Layer）**：处理控制流程——连接参数更新、加密、PHY 切换、信道图更新。它是协议逻辑，运行在中断或延迟过程调用中，不直接操作射频寄存器。
- **实时收发层（Lower Link Layer）**：在射频中断中完成事件准备、收发、帧间隔切换。硬实时，优先级最高。
- **调度层（Ticker）**：用硬件计数器计算每个连接事件的下一个锚点，提前预约射频资源。

规范文档给出的执行优先级阶梯（数字越小越优先）值得记住：事件处理 < 事件准备 < 收发完成 < 发送请求 < 角色管理 < Host。**Host 永远最后。** 这条规则解释了大量现象：应用层一次耗时数十毫秒的操作，若未做隔离，会直接吞掉若干个连接事件。

### 4.2 连接事件的时间预算

以一个 7.5 ms 间隔、1M PHY、251 字节载荷的连接事件为例，逐项拆解时间开销：

| 项目 | 时长 | 说明 |
|---|---|---|
| 主从数据包 | 2096 µs | 8 字节开销 + 251 载荷，1 µs/字节 |
| 帧间隔 tIFS | 150 µs | 规范固定值 |
| 从机空包确认 | 88 µs | 11 字节空包 |
| 单次往返 | 2334 µs | 上述三项之和 |
| 事件内往返次数 | 3 次 | 7002 µs，剩余约 500 µs |
| 有效载荷 | 753 字节 | 3 × 251 |

同样的载荷换到 2M PHY，单包时长降为 1048 µs，往返 1286 µs，事件内可完成 5 次，有效载荷 1255 字节。这解释了为什么 2M PHY 的收益接近翻倍，而不仅仅是"速度乘二"——它同时提升了每个事件内的包数。

编码 PHY（S=8）则完全改变量级：单包时长达 16.8 ms，已超过 7.5 ms 间隔，一个事件只能容纳一个包，且连接间隔必须相应放大。此时任何以"提高 PHY 速率"为目标的调优都是无效的，必须转向减少重传与提高单包有效载荷占比。

### 4.3 吞吐上限推导

在单连接、单向、无重传的理想条件下，吞吐上限可近似表达为：

> 吞吐 ≈ 每事件包数 × 单包有效载荷 ÷ 连接间隔

其中每事件包数由连接间隔、包时长与帧间隔共同决定。该式给出三个调优杠杆，且**必须同时考虑**：

- 缩短间隔：提高事件频率，但增加功耗与调度压力；
- 增大载荷：提高单包效率，依赖数据长度扩展与对端支持；
- 提升 PHY：缩短包时长，间接增加每事件包数。

三个杠杆中，只有第一个会同时提升功耗。因此产品调优的常见做法是固定间隔、提升单包效率，而测试必须验证"在目标功耗约束下，吞吐是否达到设计值"。

### 4.4 延迟分解

从应用调用写接口到数据出现在空口，延迟由五段构成：

| 阶段 | 典型量级 | 可变性 |
|---|---|---|
| Host 编码与排队 | 数十微秒 | 低 |
| 发送线程调度 | 数十至数百微秒 | 中，受优先级与队列影响 |
| HCI 传输 | 10 µs（内存直调）至 2.6 ms（1 Mbaud UART） | 高 |
| 等待下一个锚点 | 平均半个连接间隔 | 高，由间隔主导 |
| 空口传输 | 1–2 ms | 中 |

对低延迟场景，第二段与第四段是主要矛盾。而第四段给出了一个不可绕过的结论：**端到端延迟不可能低于半个连接间隔**。这也是规范 6.2 引入更短连接间隔的直接动机。

### 4.5 中断延迟与外部阻塞

射频中断必须在一个帧间隔内完成收发切换。若硬件支持外设互联（如把定时器比较事件直接连到射频任务），切换本身不占 CPU，但**中断响应的延迟仍受 CPU 状态影响**。三类常见阻塞源：

1. **Flash 擦写**：单页擦除可达数十毫秒，期间若屏蔽中断，将连续丢失多个连接事件。
2. **其他高优先级中断**：如高速外设 DMA 完成中断，若优先级高于射频中断会推迟其响应。
3. **临界区**：应用在持锁状态下长时间操作。

这三类问题的共同特征是**偶发、与负载相关、难以稳定复现**，且现象统一为"信号强度正常但周期性丢包"。诊断方法是在射频中断入口打 GPIO 翻转，用示波器测量中断间隔的抖动分布——这比任何日志都直接。

## 5 测试该往哪里使劲

关于 BLE 测试的文章通常会先给一个"测试金字塔"，再列几十条用例。这类清单看着完备，落到项目里往往变成覆盖率数字的堆砌。更实际的两个问题其实是：预算有限时先测什么，以及哪些测试根本测不出东西。

### 5.1 分层的现实

单元测试只对自研协议栈有意义。如果用的是 Zephyr 或厂商提供的栈，能动的是配置和集成层，单元层能测的只剩自己的回调，投入产出不成比例。真值得写单元测试的，是那些"看起来太简单所以没人测"的时间计算——窗口扩展、SDU 呈现时刻、参数协商的边界条件。

一致性测试要摆正位置：它是准入门槛，不是质量指标。通过 PTS 只说明实现了规范里的命令和流程，不说明八条连接并发时还能工作。把 PTS 成绩当质量结论，是不少项目后期的共同误判。

系统级与场测的反馈最真实，但慢、不可控，也不适合放进迭代节奏里。

剩下的是 HCI 边界的资源与时序。这一层没有标准工具，判据要自己定，缺陷还不稳定复现，于是最容易被跳过。我的判断很直接：预算应该优先压在这里，因为现场问题几乎都从这里长出来。

### 5.2 看得见什么，看不见什么

| 层 | 可观测内容 | 主要工具 | 固有盲区 |
|---|---|---|---|
| 应用 | 业务状态、回调时序 | 日志、打点 | 看不到协议细节 |
| Host 栈 | 连接、GATT 事务、配对状态 | 栈内日志、追踪钩子 | 看不到空口重传 |
| HCI | 全部命令、事件、ACL/ISO 分组 | 抓包（btsnoop、btmon） | 看不到时序精度 |
| 空口 | 实际 PDU、时序、信道、RSSI | 专业空口分析仪、嗅探器 | 看不到 Host 内部决策 |
| 射频 | 功率、频偏、调制质量 | 综测仪、频谱仪 | 看不到协议语义 |

这张表的用法是交叉验证，不是"挑一个工具用"。只在一层找根因，基本都会误判。典型的一条链是：HCI 抓包看到"包发了、没回"，空口抓包确认"确实没回"，射频指标显示回包频偏超标，才知道问题在晶振而不是协议栈。

### 5.3 几条真正值钱的用例

如果只能留少量用例，我会留下面八条。它们的共同逻辑很简单：都能把资源或时间逼到边界，而边界失效才是现场问题的来源。

| 编号 | 要逼出什么 | 怎么逼 | 看什么 |
|---|---|---|---|
| A-1 | 发送缓冲耗尽后的恢复 | 持续写满直至返错，再恢复写入 | 能否自愈，吞吐是否回到原值 |
| A-2 | 流控信用泄漏 | 单向满速跑两小时 | 吞吐是否随时间下降 |
| A-3 | 三处长度参数不自洽 | 协商 MTU 512，ACL 缓冲保持 27 | 是否静默分片、有效载荷是否缩水 |
| A-4 | 事件临界插入 | 在锚点前微秒窗口发起参数更新 | 事件是否被丢弃、更新是否失败 |
| A-5 | Flash 擦写干扰 | 连接态下连续擦写 | 丢包是否成簇、是否断连 |
| A-6 | 多连接调度 | 八条连接同跑 7.5 ms 间隔 | 是否有连接系统性错过事件 |
| A-7 | 传输层丢字节 | UART 随机丢字节 | H5 能否恢复、H4 报错是否明确 |
| A-8 | 长时老化 | 72 小时循环连断 | 内存与句柄是否单调增长 |

这八条要手工设计、手工判读，因为判据往往不是对错，而是"是否可恢复""是否有界"。其余功能用例不必逐条设计，交给一致性套件和回归脚本就够了。

### 5.4 指标不必多

四个数足够：吞吐（看与理论值的比值，不看绝对值）、重传率（超过 5% 通常说明事件排不下）、事件间隔抖动（用标准差，别用平均）、异常恢复时间。再多也没人看，而且会掩盖真正该盯的那一个。

### 5.5 自动化能覆盖的其实有限

值得先做的只有两件：HCI 回放和虚拟控制器。前者把"难以复现的事件序列"变成可重复输入，后者让 CI 在没有硬件时也能跑协议回归。

端到端脚本的维护成本常被低估——它们绑测试仪固件版本、绑时序、绑环境，半年后基本没人敢改。原则是只自动化"判定明确且会反复回归"的项，其余留在手工清单里，别硬凑覆盖率。

维度上也只强调两个：参数取极值，以及在锚点前插入操作。其余维度多数时候是重复劳动。

## 6 缺陷模式库

下表把常见症状映射到根因与归属层，可作为排障时的第一层过滤。

| 症状 | 高概率根因 | 归属层 | 确认手段 |
|---|---|---|---|
| 吞吐只有理论值一半 | 事件内只发一包，未用数据长度扩展 | Controller / 配置 | 抓包看单包长度与事件内包数 |
| 吞吐随时间下降 | 流控信用泄漏 | HCI | 统计未完成包数与吞吐趋势 |
| 大包写入返回内存不足 | 发送缓冲不足或尺寸小于 MTU | Host 配置 | 比对三处长度参数 |
| MTU 协商成功但吞吐不变 | 下层 ACL 缓冲截断，走分片 | Host 配置 | 抓包看 ACL 长度 |
| 周期性丢包但 RSSI 正常 | Flash 操作或临界区阻塞中断 | Controller / 应用 | GPIO 打点测中断抖动 |
| 偶发断连，无明确原因码 | 监督超时，事件被系统性错过 | Controller 调度 | 多连接压力下复现 |
| 通知偶尔丢失 | 用了 Notification 传关键数据 | Host / 设计 | 空口确认无该包 |
| 扫描报告缺失 | 事件缓冲不足或解析器不认识新子事件 | Host / 工具 | 提高缓冲后对比 |
| 配对后需重新配对 | 绑定信息未持久化 | Host | 重启验证 |
| 跨核版本不匹配 | 两侧固件 HCI 扩展不一致 | 部署 | 统一版本后复测 |
| 串口直连时吞吐上不去 | UART 波特率成为瓶颈 | 传输层 | 计算传输耗时占间隔比例 |
| 加密后吞吐骤降 | MIC 使有效载荷减少，且加密流程占用事件 | Controller | 加密前后对比 |
| 编码 PHY 下连接不稳 | 间隔不足以容纳单包 | 配置 | 检查间隔与包时长关系 |
| 广播发不出去且无报错 | 扩展广播特性未在 Controller 使能 | 配置 / Controller | 检查特性位图与命令返回 |

## 7 Zephyr 与常规 RTOS 环境的差异

Zephyr 本身就是 RTOS，所以"Zephyr 和 RTOS 有什么区别"这个问法并不成立。真正有意义的问题是：同样跑 BLE 协议栈，Zephyr 与"FreeRTOS 加厂商 SDK"、"Linux 加 BlueZ"这两种常见环境，工程处境差在哪。差别不在功能，而在三件事——谁掌握栈的内部、谁定义线程、以及出问题时你能看见什么。

### 7.1 栈、驱动、内核在同一棵树里

厂商 SDK 里的协议栈通常是二进制库加一张回调表：能改的只有初始化参数和回调实现，线程优先级、栈大小、缓冲数量都封在库里，出问题只能靠现象反推。

Zephyr 把这些全摊开。`bt_send()` 往下是 HCI 驱动，再往下是链路层，可以一路单步进去；缓冲数量、线程优先级、事件调度策略都是 Kconfig。这既是它最大的价值，也是最大的风险——所有东西都能改，也就都能改坏。我遇到过最典型的一类现象是"同一个问题换个 commit 就复现不了"，查到最后不是代码变了，是配置漂移了。

所以用 Zephyr 做 BLE，第一件事不是写测试，而是把配置冻成基线：west manifest 固定版本，`prj.conf`、overlay、最终 `.config` 三个文件一起入库，测试报告必须能指到具体的那份 `.config`。否则后面所有对比都失去意义。

### 7.2 线程是栈定义的，不是你定义的

这是与常规 RTOS 差得最远的一点。FreeRTOS 里任务是你建的、优先级是你定的，协议栈只是被调用的库；Zephyr 里，Host 的接收线程、发送线程、系统工作队列，加上 Controller 的中断与延迟过程调用，全部由栈在初始化时创建，优先级是 Kconfig 里的隐藏项——接收线程 8，发送线程 7，都是协作式优先级。

协作式的含义是：同优先级之间不做时间片轮转，只被更高优先级或中断抢占。于是同一段耗时 20 ms 的代码，在 FreeRTOS 上最坏是"低优先级任务饿死"，在 Zephyr 的 BT 线程上就是"连接事件被吞掉、对端超时断连"。

测试上的推论很直接：不要只测功能，要测最坏执行时间。用 DWT 周期计数器或者 GPIO 打点，量每个回调的耗时分布，取 P99 而不是平均值。这件事做一遍，往往能解释掉一批"偶发断连"。

### 7.3 没有进程边界

Linux 上跑 BlueZ，Host 是用户态进程，崩了不牵连内核，Controller 是独立芯片，物理隔离。Zephyr 是单地址空间：Host 的线程栈溢出，踩到的是 Controller 的缓冲或者内核对象。现象就变成了"随机断连""配对后立刻断开""广播突然发不出去"，而根因可能只是一个三百字节的栈溢出。

这直接改变了测试重心。Linux 侧你关心进程是否还活着；Zephyr 侧你必须关心每个线程的水位。开线程分析器、开栈保护、长时测试后看高水位，这些动作的价值高于多数功能用例。

### 7.4 设备树是编译期契约

常规 RTOS 用宏和初始化代码配外设，写错了运行时还能改。Zephyr 用设备树，引脚、外设、时钟源在编译期就定死。冲突不会在运行时报警，只会变成"串口没数据"或者"连上以后周期性丢包"。

我见过最隐蔽的一例是低频时钟源选错：默认走内部 RC，睡眠时钟精度的偏差被算进窗口扩展，表现是连接维持几分钟后丢包率缓慢上升，而 HCI 抓包完全正常。这类问题的入口不在协议层，在 overlay 文件里。

### 7.5 几种形态共用一套代码，但不共用一套判据

Zephyr 可以只做 Host、只做 Controller，或者两者合体。代码复用度很高，判据却不能复用：合体形态看中断时序与共享资源，双核形态看跨核消息与版本一致性，纯控制器形态看传输可靠性与流控。同一份用例套到不同形态上，很容易得到一个"通过"的假结论。

### 7.6 什么时候它并不合适

如果目标只是做一个稳定的 BLE 外设、不打算动协议栈，厂商 SDK 在成熟度、认证资料和 FAE 支持上仍然更省事。Zephyr 的收益来自"可控"和"跨芯片复用"，代价是集成风险由你自己承担。这个取舍应该在立项时说清楚，而不是等到联调阶段才发现没人读得懂链路层。

## 8 Zephyr 平台的落地要点

落地时有两个前提最容易被跳过：Controller 是谁的，以及固件跑在哪种部署形态里。前者决定出问题时你能改到哪一层，后者决定 HCI 到底长什么样。

### 8.1 控制器从哪来

讨论"Zephyr 上的 BLE"时容易漏掉一件事：手里的 Controller 未必是 Zephyr 的。除了用 `CONFIG_BT_CTLR` 编开源链路层，另一种更常见的情况是芯片厂商买了第三方 IP，把基带和固件封在芯片里，Zephyr 只做 Host。

这个市场高度集中。法国的 RivieraWaves 在 2014 年被以色列 CEVA 收购，产品线现在叫 Ceva-Waves Bluetooth；按 IPnest 2026 年的报告，CEVA 在无线接口 IP 占约 68% 份额，蓝牙 IP 有一百多家被授权方。国内不少 BLE SoC 的底层就是这套——汇顶 GR551x、联盛德、上海富芮坤 FR801x、炬芯等，公开资料里都能查到授权关系。Synopsys 的 DesignWare 也提供蓝牙 IP，Imagination 的 Ensigma 曾是"射频加基带整套"的主要来源，后来业务收缩了。

授权交付物的边界通常在 **HCI**：硬件基带控制器、Controller 固件、可选的 Host 栈与射频。于是当 Host 用 Zephyr、Controller 来自 IP 授权时，HCI 就是两家的接缝，也是唯一"双方都有责任、又都容易说自己没问题"的位置。

这一点会直接改变抓包的判读方式。自动化里拿 HCI ACL 做字段验证，其实横跨两层：

| 层 | 关键字段 | 归属 |
|---|---|---|
| HCI ACL | Handle、PB、BC、Length | IP 的 HCI 接口实现 |
| LL PDU | LLID、NESN、SN、MD、CP、Length | IP 的链路层实现 |

两层之间有固定映射，比如 `PB=0b11`（完整 PDU）对应 `LLID=0b10`（L2CAP 起始），`PB=0b00` 或 `0b01`（首片、续片）对应 `LLID=0b01`（续片）。这套映射做错的后果很有欺骗性：HCI 侧字段全对，空口侧却拼不出完整包，单看任何一层都查不出来。

所以两端对跑的用例里值得专门留一组分片边界：把 L2CAP PDU 卡在 251 字节前后，验证四种 PB 组合与 LLID 的映射是否与规范一致。这类问题在纯开源链路层上少见，在 IP 授权的控制器上却时有发生——因为两层往往不是同一个团队写的。

### 8.2 四种部署形态及其测试差异

Zephyr 的 HCI 在不同部署形态下是不同的事物，测试重点随之变化：

| 形态 | 典型平台 | HCI 的物理形态 | 测试重点 |
|---|---|---|---|
| 单芯片合体 | 单核 SoC | 内存中的函数调用 | 中断优先级、栈深度、共享资源竞争 |
| 双核分体 | 双核 SoC | 核间消息 | 跨核版本一致性、消息队列深度、跨核时延 |
| 纯控制器 | 独立芯片供外部 Host | 串口 / SPI / USB 字节流 | 传输可靠性、流控、复位时序 |
| 主机加外挂 | 通用 MCU 加模块 | 串口 H4/H5 | 丢字节恢复、波特率预算、初始化时序 |

第三与第四种形态的测试必须包含"传输层故障注入"这一独立维度，因为这是它们独有的失效面。第一与第二种形态则应把重点放在共享资源与中断时序上。

### 8.3 关键配置项与副作用

Zephyr 的默认配置偏向"最小可用"，直接用于性能或稳定性测试会产生系统性误判。以下配置项及其默认值需重点核对：

| 配置项 | 默认值 | 副作用 |
|---|---|---|
| `BT_BUF_ACL_TX_SIZE` | 27 | 等价于 ATT MTU 23，大包必然分片 |
| `BT_BUF_ACL_TX_COUNT` | 3 | 在途包仅 3 个，长往返链路上吞吐受限 |
| `BT_BUF_ACL_RX_SIZE` | 27 | 大包接收能力弱 |
| `BT_BUF_CMD_TX_COUNT` | 1 | 并发调用命令接口会串行等待 |
| `BT_BUF_EVT_RX_COUNT` | 10 | 高速扫描时事件可能丢弃 |
| `BT_RX_STACK_SIZE` | 1024 | 回调中较深调用会栈溢出 |
| `BT_HCI_TX_STACK_SIZE` | 640（合体）| 驱动内部分片或加密时可能不足 |
| `BT_HCI_ACL_FLOW_CONTROL` | 分体部署时默认开 | 关闭后接收缓冲易耗尽 |
| `BT_CTLR_TX_BUFFERS` | 3–7 | 决定 Controller 侧可排队 PDU 数 |

一条实用规则：**发送侧与接收侧的缓冲数应分别按"带宽时延积"估算**，而不是凭经验取大值。带宽时延积等于目标吞吐乘以最坏往返时延，再除以单包载荷。

### 8.4 调试抓手

按信息密度排序，四个抓手依次为：

1. **HCI 抓包**：能同时看到命令、事件、数据三类流，是唯一能重建完整状态机的视角。合体部署可用内置 btsnoop，分体部署可在传输层旁路抓取。
2. **射频中断 GPIO 打点**：把中断进入与退出映射到引脚，用示波器直接观察抖动与丢失，这是判断"是否被阻塞"的唯一直接证据。
3. **栈使用统计**：开启栈用量统计，在长时测试后检查高水位，提前发现溢出风险。
4. **特性位图对照**：读取本地支持的 LE 特性与命令位图，与 Host 期望值逐位比对，可快速定位"命令返回未知"这类配置问题。

## 9 规范演进对测试的影响

近三个版本的功能增量，几乎都落在本文强调的两个边界上：

| 版本 | 关键特性 | 对测试的新增要求 |
|---|---|---|
| 6.0 | 信道探测、帧间隔更新、链路层扩展特性集 | 测距精度与安全性测试；帧间隔变化后时序预算需重算 |
| 6.1 | 可解析私有地址随机化更新 | 地址变更时刻的分布测试；变更由控制器完成，需验证 Host 感知一致性 |
| 6.2 | 更短连接间隔、LE 直接测试模式增强、ISO over USB | 微秒级间隔下的调度能力；测试夹具可由有线改为空口 |
| 6.3 | 信道探测相位校正与测距精度改进 | 测距结果的一致性统计取代单点精度判断 |

其中影响最大的是 6.2 的连接间隔缩短。当间隔从毫秒级进入数百微秒级，前述所有时间预算表都要重算：单包时长可能超过间隔，事件内往返次数退化为 1，中断响应预算被压缩一个数量级。这类变更不是"参数调整"，而是**架构级约束变化**，必须重新做时序验证，不能沿用旧的测试基线。

另一项值得关注的是测试模式的演进。传统直接测试模式依赖两线串口夹具，新版本支持空口方式，这意味着产线测试架构可以简化，但也引入了"测试本身受射频环境影响"的新问题，需要在测试方案中评估。

## 10 结论与检查清单

BLE 协议栈的复杂度不在单层，而在层间的**契约传递**。Host 把语义翻译成命令，Controller 把命令翻译成时间与比特，而 HCI 刻意不传递时间精度、失败细节与资源状态。测试工程师的核心能力，就是为这些被丢弃的信息重建观测手段。

以下清单可作为项目评审时的快速自检：

- 三处长度参数（ATT MTU、L2CAP MTU、ACL 缓冲）是否显式核对并写入配置基线？
- 双向流控是否分别在长时压力下验证过？是否统计过吞吐随时间的趋势？
- 时序预算是否按目标 PHY 与连接间隔实际计算过，而非沿用旧项目数值？
- 是否具备在射频中断处打点的能力？是否测量过中断延迟分布而非平均值？
- 是否用 HCI 回放覆盖过异常事件序列？是否有虚拟控制器参与 CI？
- 部署形态变更（合体改分体、外挂改内置）后，是否重跑了传输层故障注入用例？
- 规范版本升级后，是否重算了时间预算，而非仅验证新命令可用？

这份清单没有权重。但如果前三条里有任何一条答"否"，后面性能与稳定性测试的结论基本不可信。
