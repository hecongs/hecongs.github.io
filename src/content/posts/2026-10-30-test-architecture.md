我没有先画一个通用测试金字塔再往上填。每一段工作都是先定「什么叫通过」，再决定自动化停在哪一层。仪器、Jenkins 和 Python 是实现。换一个产品，先问失败要分成哪几种，再决定脚本打到哪一层。

## 耳机：命令入口，日志做证据

达发这边测的是 7x 单芯片和 8x 双芯片上的 ANC、通透、PEQ。开发板经 UART 转 USB 把日志送到 PC，Wireshark 看这些日志。

通过要分成几层，不能合成「点下去有反应」：

- 命令是否送达。7x 用 Android UT App 下发，重复点击用 Selenium 收成版本回归。8x 改成 AT 命令，因为 App 点击盖不住两颗芯片的状态是否一致。
- 功能是否按模式生效。ANC、通透、PEQ 的切换、参数加载和回读要一致。冒烟只守这条主路径。
- 交互是否经得起重复。Python 对 BLE 和芯片做反复开关、反复下发，看命令丢失、状态卡死和回连失败。
- 单独的验收项。BLE 下手机多设备轮转可以完成，测得延迟小于 49ms。这项不和「命令有返回」混在一起。双芯片还要同时看延迟和音质是否优于单芯片基线。

日常版本的 Jenkins 只跑已经定死的主路径和已经自动化的操作。压力和多连结果写进测试报告，失败进 Jira。

## 无线模组：产测、协议、云端分开

涂鸦这边是 Tuya OS 上的 BLE Mesh（Silicon Labs EFR32BG24）和 ZigBee（Telink TLSR8258）。连上了不算协议正确。

产测看板级：PCBA、射频信标、GPIO、RSSI。这层失败多半是天线、匹配、供电或引脚，不是协议栈。

协议看抓包。BLE Mesh 用 RFConnect 把 Proxy、PB-ADV、PB-GATT 拆开，比较两条配网路径的步骤和成功率。主从广播要能发全、收全。Friend 和低功耗节点要在低功耗状态下看功耗，并确认友谊关系建立后消息还能送达。群组 OTA 看成功率、掉线和升级后的版本。ZigBee 用 Ubiqua 看入网时的密钥交换、多跳路由、MAC 地址、OTA 所在信道和发包时长，以及涂鸦私有协议的上报下发。

云端看规模。涂鸦云测 App 压多节点上报下发和群组响应成功率，并压 DP 点、功耗和拉距后的转发极限。P0 放到树莓派上做 HIL，通过 SSH 在 Ubuntu 上执行，Jenkins 定时跑。协议抓包和云端压测不要和这步 HIL 绑死，否则树莓派断线会把云端问题也标成环境失败。

## 语音玩具：三条判定

T5 是 WiFi + BLE 的语音陪伴玩具。整机 SOP 里，说话、对话和无线是三套标准。

- ASR 看识别。用错误率看噪声和口语下会不会掉识别，自动化负责把语音样本播出去、把识别文本收回来。
- 对话看内容。是否答非所问、多轮之后上下文是否还在、回答是否越界。
- 无线看链路。配网是否稳定，信号是否抖动，Ping 和 Iperf 看连通和吞吐，OTA 期间功耗单独记。

弱网高负载下自动看内存是否持续上涨。复杂交互和异常场景，例如打断说话、连续唤醒、配网中途掉电，留手工探索。自动化覆盖语言安全和多轮上下文，不覆盖所有异常。

## 存储芯片：结果要对上工位和失效类型

态坦这边是 TA0210 简易 ATE 和 TL1000 SLT 上的 LPDDR Pattern。上位机用 Python 写，SLT 的界面自动化用 PyQt。

通过不是一个总的 FAIL。至少分成：

- Pattern 本身。脚本自动加载程式，控制机台执行，实时收回 PASS/FAIL，并要能对上是哪一段 Pattern、哪一个工位。多工位并行时，调度和结果回收属于上位机。
- 时序。示波器和逻辑分析仪看 CLK、DQS、DQ，时钟、数据选通和数据总线是否对齐。
- 功耗。动态功耗和静态功耗的突然跳变。
- 供电。万用表看空载时 Vin 的电流和电压。
- 温度。高低温循环之后，Pattern 是否还能跑完。

这几类分开记，交给软件或硬件、FPGA 时才知道改哪边。Git 管上位机脚本，Jenkins 或 GitLab CI 在系统软件更新后跑核心项。Pattern 程式的版本跟着机台软件，不和脚本的一次断言修改绑在一起。

## Dongle 台架：关联、地址、换路由器

Windows 上的 USB WiFi 自动化沿用同一条原则。网卡关联上 SSID，只说明链路跟上了。地址要落在这台路由器的网段里，`169.254` 开头或落到别的网段，都不算连上。断开用例只检查链路已经断开，不再空等 DHCP。矩阵里预期不能连接时，即使拿到的是别的网段地址，只要仍然关联在被测 SSID 上，就判失败。

换 H3C 或小米时，用例不复制一套。H3C 用网页改无线配置，小米用 SSH。小米上下发不了的矩阵组合就跳过，例如自动信道、5G 自动频宽、160/320 MHz。2.4G 的「20/40 自动」在小米上落成 40 MHz。H3C 那次会切断测试机上网路径的重启，不要套到小米上。

流水线是这套判定的执行方式，不是架构本身。判定写错时，把回归跑得再勤，也只是在重复一个错误的通过条件。
